# Operating Systems — Memory Management & Paging Notes

> **Goal:** Strong conceptual understanding + RRB SO IT / banking IT exam revision  
> **Scope:** Memory Management topics covered so far, ending at Paging, TLB, Demand Paging and Multi-Level Paging.  
> **Not covered yet:** Page Replacement Algorithms (FIFO, Optimal, LRU, Clock), Thrashing, Working Set.

---

# 1. Why Memory Management Is Needed

When a program runs, the CPU needs instructions and data to execute.

The executable is originally stored on secondary storage:

```text
Source Code
   ↓
Compiled
   ↓
Executable / Binary
   ↓
SSD / HDD
   ↓
Program is Run
   ↓
Process is Created
```

The process gets a **virtual address space** containing regions such as:

```text
High Address
+----------------------+
| Stack                |
+----------------------+
|                      |
| Free / Mapped Area   |
|                      |
+----------------------+
| Heap                 |
+----------------------+
| BSS                  |
+----------------------+
| Data                 |
+----------------------+
| Code / Text          |
+----------------------+
Low Address
```

The OS and hardware together manage how the process's virtual memory maps to actual physical RAM.

---

# 2. Does the Entire Running Process Have to Be in RAM?

No.

In a modern virtual-memory system using demand paging:

> A process may be running even when only some of its virtual pages are currently present in RAM.

The CPU only needs the pages containing the instructions/data it is currently accessing.

Example:

```text
Process Virtual Pages

Page 0  → RAM
Page 1  → RAM
Page 2  → Not currently in RAM
Page 3  → RAM
Page 4  → Not currently in RAM
...
```

If the CPU later accesses a valid page that is not resident in RAM, a **page fault** occurs and the OS loads the required page.

---

# 3. CPU Scheduling vs Memory Management

Do not mix these two ideas.

## CPU Scheduling

States such as:

```text
Ready
Running
Waiting
```

describe the relationship of a process/thread with the CPU.

Example:

```text
Ready → Running → Waiting → Ready
```

## Memory Management

Questions such as:

```text
Which virtual page is needed?
Which RAM frame contains it?
Is the page currently resident?
```

describe where process memory resides.

Important:

> **Ready does NOT mean "on disk".**  
> **Running does NOT mean the whole process must be in RAM.**

---

# 4. Logical / Virtual Address vs Physical Address

## Virtual / Logical Address

The address generated by the CPU for a process.

Each process works as if it has its own address space.

## Physical Address

The actual location in physical RAM.

The translation is performed by the hardware memory-management unit:

```text
CPU
 ↓
Virtual Address
 ↓
MMU
 ↓
Physical Address
 ↓
RAM
```

---

# 5. MMU — Memory Management Unit

The **MMU** is hardware responsible for translating virtual/logical addresses into physical addresses.

In paging, the MMU uses information such as:

- page number
- offset
- page table
- TLB

Important wording:

> RAM is divided into frames.  
> The process address space is divided into pages.  
> The MMU itself does not "have 4 KB frames."

---

# 6. Dynamic Memory and `malloc()`

Suppose a C program does:

```c
int *p = malloc(1000);
```

Conceptually:

```text
Program requests memory
      ↓
Runtime / allocator manages process heap
      ↓
Process gets virtual address range
      ↓
OS/MMU later ensure required virtual pages map to physical frames
```

A successful `malloc()` does not necessarily mean that all corresponding physical RAM was immediately touched or loaded at that exact moment.

Modern operating systems often allocate/manage memory lazily.

---

# 7. Contiguous Memory Allocation

In contiguous allocation, a process is allocated one continuous region of physical memory.

Example:

```text
RAM

+----------+
| OS       |
+----------+
| Process A|
| Process A|
+----------+
| Process B|
| Process B|
+----------+
| Free     |
+----------+
```

Problem:

> A process may require a large continuous block even when enough free memory exists in separated locations.

This leads to fragmentation problems.

---

# 8. Fragmentation

## External Fragmentation

Enough total free memory exists, but it is scattered into small non-contiguous holes.

Example:

```text
Used | Free 5 KB | Used | Free 8 KB | Used | Free 6 KB
```

Total free memory:

```text
19 KB
```

But a process asking for a contiguous 15 KB block may not fit.

This is **external fragmentation**.

---

## Internal Fragmentation

Memory is allocated in fixed-size units, but the process may not use the entire final allocated unit.

Example:

```text
Page size = 4 KB
Process requires = 18 KB
```

Pages required:

```text
ceil(18 / 4) = 5 pages
```

Allocated:

```text
5 × 4 KB = 20 KB
```

Unused:

```text
20 - 18 = 2 KB
```

That 2 KB is **internal fragmentation**.

Important:

```text
Paging eliminates external fragmentation.
Paging may still cause internal fragmentation.
```

---

# 9. Paging — Basic Idea

Paging is a non-contiguous memory-management technique.

The process's virtual address space is divided into fixed-size units called:

**Pages**

Physical RAM is divided into fixed-size units called:

**Frames**

Important rule:

```text
Page Size = Frame Size
```

Example:

```text
Page size = Frame size = 4 KB
```

A process's pages can be placed in different physical frames:

```text
Virtual Page 0 → Physical Frame 7
Virtual Page 1 → Physical Frame 20
Virtual Page 2 → Physical Frame 3
Virtual Page 3 → Physical Frame 50
```

Pages do **not** need to be physically contiguous in RAM.

---

# 10. Why Page Size Equals Frame Size

Because a page must fit exactly into a physical frame.

Example:

```text
Page size  = 4 KB
Frame size = 4 KB
```

Then:

```text
Page 5 → Frame 12
```

The location inside the page remains the same location inside the frame.

This is why the **offset does not change** during translation.

---

# 11. Powers of Two in Paging

Page sizes are normally powers of two.

Examples:

```text
1 KB  = 2^10 bytes
2 KB  = 2^11 bytes
4 KB  = 2^12 bytes
8 KB  = 2^13 bytes
16 KB = 2^14 bytes
```

This makes address splitting easy in binary.

If:

```text
Page size = 4 KB = 2^12 bytes
```

then:

```text
Offset bits = 12
```

The MMU can treat the lower 12 bits as the offset.

---

# 12. 1 KB Means 1024 in Paging Numericals

For OS/memory-addressing numericals:

```text
1 K = 1024 = 2^10
```

Therefore:

```text
4 KB = 4 × 1024
     = 4096 bytes
     = 2^12 bytes
```

This is not an approximation in binary memory calculations.

Example:

```text
4K = 4096
5K = 5120
```

`4991` is not exactly `5K`.

---

# 13. Bit, Byte and Word

## Bit

Smallest information unit:

```text
0 or 1
```

## Byte

```text
1 byte = 8 bits
```

Most modern general-purpose systems are **byte-addressable**:

```text
1 memory address → 1 byte
```

## Word

A **word** is an architecture-related natural data unit.

It is not universally fixed.

Examples may include:

```text
16-bit word = 2 bytes
32-bit word = 4 bytes
64-bit word = 8 bytes
```

But the exact meaning depends on the architecture/question.

Important:

> Address bits tell us the number of **addressable locations**, not automatically the number of bytes.

If memory is byte-addressable:

```text
12-bit address
→ 2^12 addresses
→ 4096 bytes
```

If memory is word-addressable:

```text
12-bit address
→ 4096 words
```

Bytes then depend on the word size.

---

# 14. Why 4 KB Page Uses 12 Offset Bits

A 4 KB page contains:

```text
4096 bytes
```

Byte offsets are:

```text
0
1
2
...
4095
```

There are:

```text
4096 = 2^12
```

possible byte positions.

Therefore:

```text
Offset field = 12 bits
```

Important:

```text
12 offset bits ≠ offset values 0–12
```

Instead:

```text
12 bits can represent values 0–4095
```

Example:

```text
000000000000 = offset 0
000000000001 = offset 1
...
111111111111 = offset 4095
```

---

# 15. Byte Contains 8 Bits — Why Offset Still Selects a Byte

A 4 KB page contains:

```text
4096 bytes × 8 bits
= 32768 bits
= 2^15 bits
```

This is correct.

But on a byte-addressable machine, the CPU addresses **bytes**, not individual bits.

Therefore:

```text
Page Offset selects one of 4096 bytes
```

not one of 32768 individual bits.

Example:

```text
Page 3
Offset 2
```

means:

```text
third byte of Page 3
```

because offsets are normally zero-based:

```text
Offset 0 → first byte
Offset 1 → second byte
Offset 2 → third byte
```

That byte contains 8 bits.

Example:

```text
Byte = 10110110
```

A CPU can manipulate a specific bit using bit masks/shifts, but each bit usually does not have its own independent memory address.

---

# 16. Virtual Address = Page Number + Offset

Suppose:

```text
Virtual Address = 32 bits
Page size = 4 KB = 2^12 bytes
```

Then:

```text
Offset bits = 12
```

Remaining bits:

```text
32 - 12 = 20
```

Therefore:

```text
32-bit Virtual Address

+----------------------+----------------+
| Page Number          | Offset         |
| 20 bits              | 12 bits        |
+----------------------+----------------+
```

---

# 17. Number of Virtual Pages

For a byte-addressable 32-bit virtual address:

```text
Total virtual address space
= 2^32 bytes
= 4 GB
```

Page size:

```text
4 KB = 2^12 bytes
```

Number of virtual pages:

```text
2^32 / 2^12
= 2^20 pages
```

So:

```text
Number of pages = 2^20
Page-number bits = 20
Offset bits = 12
```

---

# 18. Finding Page Number and Offset

Formula:

```text
Page Number = floor(Virtual Address / Page Size)

Offset = Virtual Address % Page Size
```

Example:

```text
Page size = 4096 bytes
Virtual Address = 23576
```

Then:

```text
23576 = 5 × 4096 + 3096
```

Therefore:

```text
Page Number = 5
Offset = 3096
```

---

# 19. Page Table

The page table maps virtual page numbers to physical frame numbers.

Example:

```text
Virtual Page     Physical Frame

0                21
1                 4
2                17
3                30
4                 9
5                12
```

If CPU generates:

```text
Page = 5
Offset = 3096
```

the page table says:

```text
Page 5 → Frame 12
```

Physical address becomes:

```text
Frame = 12
Offset = 3096
```

---

# 20. Physical Address Calculation

Formula:

```text
Physical Address
= Frame Number × Frame Size + Offset
```

Example:

```text
Frame = 12
Frame size = 4096 bytes
Offset = 3096
```

Then:

```text
Physical Address
= 12 × 4096 + 3096
= 52248
```

---

# 21. Offset Does Not Change

This is one of the most important paging rules.

```text
Virtual Address

[ Virtual Page Number | Offset ]
              ↓
           Page Table
              ↓
Physical Address

[ Physical Frame No. | Offset ]
```

Only:

```text
Page Number → Frame Number
```

changes.

The offset remains the same because:

```text
Page Size = Frame Size
```

---

# 22. Physical Address Bits and Frame-Number Bits

Suppose:

```text
Physical Address = 16 bits
Frame size = 4 KB = 2^12 bytes
```

Physical address space:

```text
2^16 bytes = 64 KB
```

Number of frames:

```text
2^16 / 2^12
= 2^4
= 16 frames
```

Therefore:

```text
Frame-number bits = 4
Offset bits = 12
```

Physical address structure:

```text
+----------------+----------------------+
| Frame Number   | Offset               |
| 4 bits         | 12 bits              |
+----------------+----------------------+
```

Rule:

```text
Physical Address Bits
=
Frame-Number Bits + Offset Bits
```

---

# 23. Pages vs Frames — Exam Trap

Use these words carefully.

```text
Logical / Virtual Address Space
→ divided into Pages

Physical Address Space / RAM
→ divided into Frames
```

If you calculate:

```text
Physical Address Space / Frame Size
```

you get:

```text
Number of Frames
```

not number of pages.

---

# 24. Example: Logical and Physical Address Math

Given:

```text
Logical Address = 13 bits
Physical Address = 12 bits
Page size = Frame size = 1K words
```

Assuming word-addressable memory:

```text
Logical Address Space
= 2^13 words
= 8K words
```

Physical Address Space:

```text
2^12 words
= 4K words
```

Page/frame size:

```text
1K words = 2^10 words
```

Number of virtual pages:

```text
2^13 / 2^10
= 2^3
= 8 pages
```

Number of physical frames:

```text
2^12 / 2^10
= 2^2
= 4 frames
```

Address formats:

```text
Logical Address:
[ Page Number: 3 bits | Offset: 10 bits ]

Physical Address:
[ Frame Number: 2 bits | Offset: 10 bits ]
```

# 25. Page Table Entry (PTE)

A Page Table Entry contains more than only the physical frame number.

Conceptually:

```text
+------------+---------+-------+-----------+------------+
| Frame No.  | Present | Dirty | Reference | Protection |
+------------+---------+-------+-----------+------------+
```

Typical fields include:

- physical frame number
- present/valid bit
- dirty/modified bit
- accessed/reference bit
- protection bits

Actual PTE layouts depend on architecture.

---

# 26. Present / Valid Bit

Conceptually:

```text
Present = 1
→ page is currently resident in RAM
```

```text
Present = 0
→ page cannot currently be translated to a resident physical frame
```

If the address is valid for the process but the required page is not resident:

```text
Page Fault
```

occurs.

---

# 27. Dirty / Modified Bit

Suppose a page is loaded from its backing source into RAM.

Initially:

```text
Dirty = 0
```

If CPU modifies data in that page:

```text
Dirty = 1
```

Meaning:

> RAM copy has been modified relative to its backing copy.

When OS wants to evict a page:

```text
Dirty = 0
→ may be discarded if backing copy is already usable
```

```text
Dirty = 1
→ modified data may need to be written back before reuse of the frame
```

This is why it is called the **dirty bit** or **modified bit**.

---

# 28. Reference / Accessed Bit

The reference/accessed bit tells whether a page has been accessed recently.

Conceptually:

```text
Reference = 1
→ page was recently accessed
```

This information can be used by page-replacement algorithms such as:

```text
Second Chance / Clock
```

Important distinction:

```text
Dirty Bit
→ Was the page modified?

Reference Bit
→ Was the page accessed recently?
```

---

# 29. Protection Bits

Protection information can indicate whether a page is allowed to be:

```text
Read
Write
Execute
```

Example:

```text
Code page → Read + Execute
Data page → Read + Write
```

Attempts to violate page permissions can cause a protection fault.

---

# 30. Why a Simple Page Table Can Be Expensive

Suppose:

```text
32-bit virtual address
4 KB page size
```

Virtual pages:

```text
2^20
```

If every PTE occupies 4 bytes:

```text
Page table size
= 2^20 × 4 bytes
= 4 MB
```

This can be large for a single process, especially when much of the virtual address space is unused.

This motivates **multi-level paging**.

---

# 31. TLB — Translation Lookaside Buffer

A normal page-table lookup may require an extra memory access.

Without TLB:

```text
1. Access page table in RAM
2. Access actual data in RAM
```

So one program memory reference may require two physical memory accesses.

The **TLB** is a small, very fast cache of recent address translations.

Example:

```text
TLB

Virtual Page   Physical Frame
5              12
2               7
9              22
1               4
```

---

# 32. TLB Hit

CPU needs:

```text
Page 5
```

TLB already has:

```text
Page 5 → Frame 12
```

Then:

```text
TLB Hit
```

The MMU can use the cached translation without first walking the page table.

---

# 33. TLB Miss

If the page mapping is not present in TLB:

```text
TLB Miss
```

Then the MMU/page-walk mechanism checks the page table.

Important exam trap:

```text
TLB Miss ≠ Page Fault
```

Example:

```text
TLB:
Page 7 → not found

Page Table:
Page 7 → Frame 20
Present = 1
```

Result:

```text
TLB Miss
No Page Fault
```

---

# 34. Page Fault

A page fault happens when the required valid virtual page is not currently resident in physical memory.

Conceptual flow:

```text
CPU accesses virtual address
        ↓
TLB / Page Table translation
        ↓
Page not resident
        ↓
Page Fault
        ↓
OS takes control
        ↓
Check whether address is valid
        ↓
Find/load required page
        ↓
Place page in physical frame
        ↓
Update page table
        ↓
Restart faulting instruction
```

A page fault is not automatically an error.

It can be normal virtual-memory behavior.

---

# 35. Page Fault vs Segmentation Fault

## Valid but Nonresident Page

```text
Address belongs to process
Page not in RAM
```

Result:

```text
Page Fault
```

OS may load the page and continue execution.

## Invalid / Unauthorized Address

If the program accesses memory it is not allowed to access:

```text
Invalid memory access
```

The OS may terminate it.

On Unix-like systems, this may appear as:

```text
Segmentation fault
```

Important:

```text
Page Fault ≠ Segmentation Fault
```

---

# 36. Demand Paging

Demand Paging means:

> Load a page into RAM only when it is actually needed.

Example:

```text
Process has many virtual pages

Currently resident:
P0
P1
P4
P10

Not currently resident:
P2
P3
P5
P6
...
```

If CPU accesses a nonresident valid page:

```text
Page Fault
```

Then the OS loads it.

Benefits:

- less RAM required initially
- faster initial loading
- more processes can coexist
- unused virtual regions need not consume physical RAM

---

# 37. Where Are Nonresident Pages?

For learning purposes, think:

```text
Not in RAM
→ backing storage / secondary storage
```

But technically different pages may come from different backing sources:

- executable file
- mapped file
- swap/pagefile
- zero-filled pages created on demand
- other OS-managed backing mechanisms

So do not assume every missing page exists as one literal "process page file."

---

# 38. Page-Fault Runtime Flow

```text
CPU accesses Page X
        ↓
TLB lookup
        ↓
Page-table walk if required
        ↓
Is page resident?
       / \
     Yes  No
      |    |
      |  PAGE FAULT
      |    |
      |  OS checks validity
      |    |
      |  Find physical frame
      |    |
      |  Load required page
      |    |
      |  Update page table
      |    |
      |  Retry instruction
      |    |
      +----+
        ↓
      Continue
```

If no free frame exists, the OS must eventually choose some page to replace.

That topic is **Page Replacement**, which we have not studied yet.

---

# 39. Why Demand Paging Works — Locality

Programs usually show **locality of reference**.

## Temporal Locality

Recently accessed memory is likely to be accessed again.

Example:

```text
loop counter
frequently used variable
```

## Spatial Locality

Nearby memory locations are likely to be accessed soon.

Example:

```c
for (i = 0; i < 1000; i++)
    sum += arr[i];
```

Array elements are stored close together.

One loaded page may therefore satisfy many nearby accesses.

---

# 40. Effective Access Time with TLB

Suppose:

```text
TLB lookup = t
Memory access = m
TLB hit ratio = h
```

On TLB hit:

```text
t + m
```

On TLB miss in a simple single-level page table:

```text
t + 2m
```

Therefore:

```text
EAT
= h(t + m)
+ (1 - h)(t + 2m)
```

Example:

```text
TLB = 10 ns
Memory = 100 ns
Hit ratio = 80%
```

Hit:

```text
110 ns
```

Miss:

```text
210 ns
```

EAT:

```text
0.8 × 110 + 0.2 × 210
= 88 + 42
= 130 ns
```

# 41. Multi-Level Paging — Why It Is Needed

Single-level page tables can be very large.

Example:

```text
32-bit virtual address
Page size = 4 KB
```

Number of pages:

```text
2^20
```

If each PTE is 4 bytes:

```text
Single page table = 4 MB
```

A process may use only a small fraction of its virtual address space.

Multi-level paging reduces the page-table memory that must actually be allocated.

---

# 42. Multi-Level Paging Does Not Reduce Virtual Address Space

Important:

> Multi-level paging does NOT reduce the number of possible virtual addresses/pages.

It reorganizes the page table hierarchically.

Before:

```text
[ Page Number: 20 bits ][ Offset: 12 bits ]
```

After two-level paging:

```text
[ L1 Index: 10 ][ L2 Index: 10 ][ Offset: 12 ]
```

Still:

```text
10 + 10 + 12 = 32 bits
```

CPU still generates full 32-bit virtual addresses.

---

# 43. Why 10 + 10 + 12?

Given:

```text
Page size = 4 KB = 2^12 bytes
```

Therefore:

```text
Offset = 12 bits
```

Remaining page-number bits:

```text
32 - 12 = 20 bits
```

Suppose a PTE is 4 bytes.

One 4 KB page-table page can store:

```text
4096 / 4
= 1024 entries
= 2^10 entries
```

Therefore 10 bits can index one page-table level.

So:

```text
20 VPN bits
→ 10-bit L1 index
+ 10-bit L2 index
```

---

# 44. Two-Level Paging Structure

```text
32-bit Virtual Address

+-------------+-------------+-------------+
| L1 Index    | L2 Index    | Offset      |
| 10 bits     | 10 bits     | 12 bits     |
+-------------+-------------+-------------+
```

L1:

```text
2^10 = 1024 entries
```

Each L1 entry can point to one L2 page table.

Each L2 table:

```text
2^10 = 1024 entries
```

Maximum page mappings:

```text
2^10 × 2^10
= 2^20 pages
```

Exactly the same number of virtual pages as before.

---

# 45. Multi-Level Paging Lookup

Suppose CPU generates:

```text
L1 = 3
L2 = 7
Offset = 500
```

Lookup:

```text
L1Table[3]
       ↓
Address of some L2 Page Table
       ↓
L2Table[7]
       ↓
Physical Frame Number
       ↓
[ Frame Number | Offset 500 ]
       ↓
RAM
```

---

# 46. L1/L2 Values Are Indexes, Not Pages

If the L1 field is 10 bits:

```text
Possible L1 indexes = 0–1023
```

If the L2 field is 10 bits:

```text
Possible L2 indexes = 0–1023
```

Do not say:

```text
L1 has 2^10 pages
```

Better:

```text
L1 has 2^10 entries
```

The L2 entries eventually map virtual pages to physical frames.

---

# 47. Example: Virtual Address = 2^20

Given:

```text
32-bit VA
Page size = 4 KB = 2^12
Virtual Address = 2^20
```

Page number:

```text
2^20 / 2^12
= 2^8
= 256
```

Offset:

```text
0
```

Now split VPN 256 into:

```text
L1 index = 0
L2 index = 256
Offset = 0
```

So:

```text
VA = 2^20
→ [L1 = 0][L2 = 256][Offset = 0]
```

---

# 48. Example: Virtual Page Number = 5000

Since each L2 table contains:

```text
1024 entries
```

For VPN 5000:

```text
L1 index
= floor(5000 / 1024)
= 4
```

```text
L2 index
= 5000 % 1024
= 904
```

So:

```text
VPN 5000
→ L1 = 4
→ L2 = 904
```

---

# 49. Main Benefit of Multi-Level Paging

Single-level page table:

```text
One giant structure
with entries for a huge virtual address space
```

Multi-level paging:

```text
L1 Entry 0   → L2 table exists
L1 Entry 1   → absent / not needed
L1 Entry 2   → absent / not needed
...
L1 Entry 500 → L2 table exists
```

If a large virtual region is unused, its lower-level page table does not need to be allocated.

Therefore:

> Multi-level paging mainly saves **page-table memory**, especially for sparse virtual address spaces.

Tradeoff:

> More page-table levels can require more memory accesses on a TLB miss.

This makes the TLB even more important.

---

# 50. Single-Level vs Multi-Level Paging

## Single-Level

```text
VPN
 ↓
One Page Table
 ↓
Frame
```

Advantage:

- simple lookup

Disadvantage:

- potentially huge page table

## Multi-Level

```text
VPN split into multiple indexes
 ↓
L1
 ↓
L2
 ↓
Frame
```

Advantage:

- allocate lower-level page tables only where needed
- saves page-table memory

Disadvantage:

- more page-table accesses when translation is not cached

# 52. Most Important Formulas

## Page Offset Bits

For byte-addressable memory:

```text
Offset bits = log2(Page Size in Bytes)
```

Example:

```text
4 KB = 2^12 bytes
→ Offset = 12 bits
```

---

## Number of Virtual Pages

```text
Virtual Pages
=
Virtual Address Space / Page Size
```

For `n`-bit virtual address:

```text
Virtual pages
=
2^n / Page Size
```

Example:

```text
32-bit VA
4 KB = 2^12 page
```

```text
Pages = 2^32 / 2^12 = 2^20
```

---

## Page Number and Offset

```text
Page Number = floor(VA / Page Size)

Offset = VA % Page Size
```

---

## Physical Address

```text
PA = Frame Number × Frame Size + Offset
```

---

## Number of Frames

```text
Frames
=
Physical Address Space / Frame Size
```

---

## Frame-Number Bits

```text
Frame bits
=
Physical Address Bits - Offset Bits
```

---

# 53. Common Exam Traps

### Trap 1

```text
4 KB page has 2^15 bits
```

True as total stored bits.

But:

```text
Offset = 12 bits
```

on a byte-addressable system because there are `2^12` addressable bytes.

---

### Trap 2

```text
12 offset bits → offsets 0–12
```

Wrong.

Correct:

```text
12 bits → 2^12 values → offsets 0–4095
```

---

### Trap 3

```text
TLB miss = page fault
```

Wrong.

TLB miss only means translation was not found in TLB.

---

### Trap 4

```text
Paging removes all fragmentation
```

Wrong.

Paging:

```text
Eliminates external fragmentation
May cause internal fragmentation
```

---

### Trap 5

```text
Physical address space / page size
= number of pages
```

Wrong terminology.

Physical memory uses:

```text
Frames
```

Virtual/logical address space uses:

```text
Pages
```

---

### Trap 6

```text
Multi-level paging reduces the number of virtual pages
```

Wrong.

It reduces page-table memory usage.

---

### Trap 7

```text
10-bit L1 means 2^10 pages at first level
```

Better wording:

```text
2^10 L1 entries
```

Each L1 entry may reference another page table.
